# ConcertTicketsApi — практическая работа №3, вариант 15

Вариант — концертная площадка и продажа билетов по секторам. Проект разделяет площадку, события, сектора, ценовые категории, покупателей и билеты. Подробные шаги установки находятся в [УСТАНОВКА.md](УСТАНОВКА.md).

## Что реализовано

- SQLite и EF Core с двумя миграциями: начальная схема и изменение с токеном версии сектора, уникальными индексами билета и покупателя, индексом каталога событий.
- Начальное наполнение — 45 событий, секторы и ценовые категории; часть событий без спонсора показывает необязательную связь.
- DTO для операций API. Служебный штрихкод билета создаёт сервер и не возвращает в открытых ответах.
- Асинхронные создание и чтение, фильтрация, проекция, обновление сектора с токеном версии, безопасное удаление спонсора.
- Обычная пагинация каталога событий (`Skip/Take`) и выборка после составного курсора `StartsAt + Id`.
- Загрузка `Ticket → Sector → Event → Venue`, отдельная загрузка связи, явная дозагрузка коллекции билетов сектора.
- Демонстрационные маршруты N+1 и исправленный вариант; запрос `/api/events/sql-preview` выводит SQL без исполнения. EF Core пишет SQL в консоль.
- Продажа создаёт билет и увеличивает остаток сектора в транзакции. Возврат до начала события меняет билет и остаток вместе; конфликт откатывает транзакцию.
- Оптимистическая конкуренция через `Sector.Version`: устаревшее изменение возвращает 409.
- Аналитическая справка по выручке сектора использует параметризованный SQL.
- Состояния отслеживания: новые сущности — `Added/INSERT`, загруженный и измененный сектор — `Modified/UPDATE`, удаленный спонсор — `Deleted/DELETE`, `AsNoTracking` — `Detached` без SQL `UPDATE` при изменении в памяти.

## Запуск

Swagger: `https://localhost:7261/swagger`. SQLite файл `concerts.db` и начальные записи создаются при первом запуске.

## Основные маршруты

| Действие | Маршрут |
|---|---|
| Страница афиши | `GET /api/events?page=1&pageSize=10&status=Scheduled` |
| Следующая порция | `GET /api/events/after?afterStartsAt=...&afterId=...` |
| Создать событие | `POST /api/events` |
| Событие с площадкой и спонсором | `GET /api/events/{id}` |
| SQL проекции | `GET /api/events/sql-preview` |
| N+1 / вариант с секторами | `GET /api/events/n-plus-one`, `GET /api/events/with-sectors` |
| Прочитать версию сектора | `GET /api/sectors/{id}` |
| Изменить сектор с проверкой версии | `PUT /api/sectors/{id}` |
| Дозагрузить билеты сектора | `GET /api/sectors/{id}/tickets/explicit` |
| Продать билет | `POST /api/tickets` |
| Билет только с сектором / полная цепочка | `GET /api/tickets/{id}/with-sector`, `GET /api/tickets/{id}/details` |
| Вернуть билет | `POST /api/tickets/{id}/refund` |
| Выручка по событию | `GET /api/reports/events/{eventId}/sector-revenue` |
| Проверка AsNoTracking | `GET /api/diagnostics/no-tracking-experiment/{eventId}` |

Готовые запросы для REST Client находятся в [requests.http](requests.http). На свежей базе начальные идентификаторы: событие `1`, сектор `1`, ценовые категории `1` и `2`, покупатели `1`–`3`.

Индекс `IX_ConcertEvents_Status_StartsAt_Id` ускоряет афишу с фильтром по статусу и дате, упорядоченную по `StartsAt, Id`. Второй ключ сортировки делает порционную выдачу устойчивой.
