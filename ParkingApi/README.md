# ParkingApi — вариант 15

ASP.NET Core Web API для парковки: `ParkingSpot` — машиноместо, `ParkingBooking` — бронь. API использует SQLite и EF Core migrations. При запуске автоматически выполняется `Database.Migrate()`.

Установка .NET SDK, NuGet-пакетов и EF CLI пошагово описана в [УСТАНОВКА.md](УСТАНОВКА.md).

## Запуск

### Установка зависимостей

1. Установите .NET 10 SDK и откройте `ParkingApi.csproj` в Visual Studio 2022 либо откройте терминал в папке `ParkingApi`.
2. Восстановите NuGet-пакеты командой `dotnet restore`. EF Core SQLite, пакет Design и Swagger уже перечислены в `ParkingApi.csproj`.
3. Если понадобится управлять миграциями из терминала, выполните `dotnet tool restore`. Локальная согласованная версия инструмента `dotnet-ef` указана в `.config/dotnet-tools.json`.
4. Для ручного применения миграций выполните `dotnet ef database update` из папки с проектом. При обычном старте приложение также применяет имеющиеся миграции автоматически.

### Запуск

Нужен .NET 10 SDK. Из этой папки выполните:

```powershell
dotnet restore
dotnet run
```

Swagger: `https://localhost:7047/swagger`. База `parking.db` создаётся рядом с проектом. Если запускаете через Visual Studio, разрешите доверие локальному HTTPS-сертификату при первом запросе.

## Модель и проверки

- У `ParkingSpot` уникальный номер и зона A/B/C. Свой `ParkingSpotNumberAttribute` принимает номера `P-01`—`P-99`.
- У `ParkingBooking` есть внешний ключ на машиноместо, госномер, начало и конец интервала и отметка об абонементе резидента.
- `CreateParkingSpotDto` использует Data Annotations и пользовательский `ValidationAttribute`. `CreateParkingBookingDto` и DTO обновления проверяются FluentValidation.
- Форма брони требует конец позже начала и длительность от 30 минут.
- Сервис бронирования отклоняет несуществующее место, бронирование резидентского места без абонемента и любое пересечение интервалов одного места. Совпадение границы допустимо: бронь, начинающаяся ровно в момент окончания предыдущей, не пересекается.
- Ошибки формы возвращают 400 `ValidationProblemDetails`; бизнес-отказы — 409 `ProblemDetails`; неожиданные сбои — обезличенный 500 `ProblemDetails`.
- `X-Correlation-ID` проходит через middleware в ответ и scope логов. Тела запросов не логируются.
- CORS разрешает только `http://localhost:5173`.

## Сценарии для сдачи

1. В Swagger создайте место, например `P-12`, зона `A`, `isResidentsOnly: false`. Успешный ответ — 201 и заголовок `X-Correlation-ID`.
2. Создайте бронь этого места на час, с госномером `А123ВС777`. Успешный ответ — 201.
3. Повторите запрос на пересекающийся интервал: должен прийти 409 `ProblemDetails`. Для проверки резидентского правила создайте место с `isResidentsOnly: true` и отправьте бронь с `hasResidentSubscription: false`.
4. Передайте в Swagger заголовок `X-Correlation-ID: 11111111-1111-1111-1111-111111111111`. Тот же идентификатор появится в заголовке ответа и в консольном логе.
5. Отправьте невалидную бронь, например с длительностью 20 минут и некорректным госномером: ожидается 400 с `errors` и `correlationId`.
6. Запустите два запроса из `cors.http`. Preflight с localhost:5173 получит разрешающий заголовок, а запрос с evil.example — нет. Успешный Execute в Swagger сам по себе CORS не проверяет: Swagger и API открыты с одного origin.

Первые четыре сценария проверяются в Swagger. Два preflight-запроса для CORS выполняются только из `cors.http`. Дополнительные тела запросов есть в `requests.http`.
