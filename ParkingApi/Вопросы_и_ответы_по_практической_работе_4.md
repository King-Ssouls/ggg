# Вопросы и ответы по практической работе 4

## Коротко о проекте

Практика №4 находится в папке `ParkingApi`, вариант 15 — парковка. Проект на ASP.NET Core Web API хранит парковочные места и брони в SQLite. Контроллеры принимают DTO, валидаторы проверяют форму, сервис применяет правила бронирования, а middleware добавляют идентификатор запроса и записывают результат в лог

Запрос на создание брони проходит так:

`HTTP-запрос → DTO и валидация → контроллер → ParkingBookingService → AppDbContext и SQLite → HTTP-ответ`

`CorrelationIdMiddleware` и `RequestLoggingMiddleware` сопровождают запрос по всему этому пути

## Общие вопросы

### 1. Что делает программа

Она позволяет создавать и просматривать парковочные места и брони, а также изменять сведения о месте или брони. При создании брони проверяет, что место существует, не занято в выбранное время и доступно клиенту по его абонементу

### 2. Какие главные сущности есть в проекте

`ParkingSpot` — машиноместо с номером, зоной и признаком «только для резидентов». `ParkingBooking` — бронь с госномером, началом и окончанием интервала и признаком абонемента. У одного места может быть много броней

### 3. Как сущности связаны друг с другом

У `ParkingBooking` есть внешний ключ `ParkingSpotId` и навигационное свойство `ParkingSpot`. У `ParkingSpot` есть коллекция `Bookings`. Такая связь в Entity Framework означает «одно место — много броней»

### 4. Что такое DTO и зачем они нужны

DTO — объект для передачи данных через API. Клиент отправляет DTO создания или обновления, а контроллер возвращает DTO ответа. Поэтому клиент не передаёт напрямую сущность базы данных, её навигационные свойства и генерируемый базой `Id`

### 5. Почему для создания и обновления разные DTO

При создании места клиент передаёт номер, зону и признак доступа. При обновлении номер менять нельзя, поэтому `UpdateParkingSpotDto` содержит только зону и признак доступа. У брони при обновлении также нельзя поменять привязанное машиноместо

### 6. Как работает создание брони

Сначала фильтр проверяет поля DTO. Затем контроллер передаёт DTO в `ParkingBookingService`. Сервис читает место и существующие брони из SQLite через `AppDbContext`, проверяет правила и сохраняет новую бронь. Контроллер возвращает `201 Created` при успехе или `409 Conflict`, если правило нарушено

## Проверки и база данных

### 7. Какие уровни проверки используются

На границе API проверяются форма и обязательные поля. В сервисе проверяются правила, для которых нужно знать состояние базы. В SQLite настроены ограничения целостности, например уникальность номера места и внешний ключ брони на место

### 8. Какие Data Annotations применены

У `CreateParkingSpotDto` атрибут `[Required]` проверяет наличие номера и зоны, а `[RegularExpression]` разрешает зоны A, B или C. Для номера места используется собственный атрибут `ParkingSpotNumberAttribute`

### 9. Что проверяет собственный атрибут номера места

Он проверяет формат `P-01`—`P-99`: буква P, дефис и две цифры. Например, `P-12` подходит, а `wrong` не подходит. При ошибке атрибут возвращает сообщение на русском языке

### 10. Что проверяет FluentValidation

Валидаторы брони проверяют положительный `ParkingSpotId`, формат российского госномера, наличие дат, окончание после начала и длительность не меньше 30 минут. Правило длительности использует одновременно `StartAt` и `EndAt`

### 11. Чем отличаются Data Annotations и FluentValidation

Data Annotations находятся рядом со свойствами DTO и подходят для простых проверок одного значения. FluentValidation хранит правила в отдельных классах и удобен для проверок нескольких полей, например длительности брони

### 12. Как приложение автоматически запускает FluentValidation

В `Program.cs` валидаторы регистрируются в контейнере зависимостей. `FluentValidationActionFilter` находит валидатор для DTO и добавляет ошибки в `ModelState`. Если ошибки есть, фильтр использует общую фабрику ответа 400 и не вызывает действие контроллера

### 13. Как проверяется пересечение броней

Бронь конфликтует с другой бронью того же места, если её начало раньше окончания существующей и её окончание позже начала существующей. В коде используются условия `StartAt < endAt` и `EndAt > startAt`. Если одна бронь заканчивается ровно тогда, когда начинается следующая, пересечения нет

### 14. Как проверяется место только для резидентов

Сервис читает свойство `IsResidentsOnly` у места. Если оно равно `true`, для создания или изменения брони требуется `HasResidentSubscription == true`. Иначе сервис возвращает бизнес-отказ, а API отвечает `409 Conflict`

### 15. Какие ограничения настроены в базе

Номер места уникален. Бронь обязательно ссылается на существующее место через внешний ключ. Для обязательных строк заданы ограничения длины. Миграция в папке `Migrations` создаёт структуру SQLite при запуске приложения

## Ошибки, middleware и CORS

### 16. Чем отличаются ответы 400, 404, 409 и 500

`400 Bad Request` означает, что поля формы не прошли валидацию; сообщения лежат в `errors`. `404 Not Found` означает, что запрошенная бронь или место не найдены. `409 Conflict` означает конфликт бизнес-правила, например занятое место. `500 Internal Server Error` означает непредвиденный сбой сервера

### 17. Что такое ProblemDetails

Это единый формат ответа об ошибке. В нём есть статус и описание проблемы, а в этом проекте также `correlationId`. В ответе 500 клиент получает общее сообщение без SQL, stack trace и подробностей исключения

### 18. Что такое Correlation ID

Это идентификатор конкретного HTTP-запроса. Middleware берёт его из заголовка `X-Correlation-ID`, если клиент его прислал, или создаёт новый через `Guid.NewGuid()`. Тот же идентификатор попадает в заголовок ответа, тело ошибки и область логирования

### 19. Correlation ID — это токен авторизации

Нет. Это метка для поиска связанных записей в логах, она не подтверждает личность пользователя и не даёт доступ к API. В проекте нет JWT, access token, refresh token, API key и middleware аутентификации

### 20. Почему в CORS разрешены любые заголовки, если токенов нет

`AllowAnyHeader()` разрешает браузеру отправлять разные заголовки только с разрешённого origin. Это правило CORS, а не проверка токена. API не читает и не проверяет заголовок `Authorization`, поэтому передача Bearer-токена сейчас не добавила бы авторизацию

### 21. Что делает RequestLoggingMiddleware

Он измеряет время обработки и записывает HTTP-метод, путь, код ответа и длительность. Middleware Correlation ID добавляет тот же идентификатор в область логирования, поэтому запрос можно найти по ID

### 22. Что делает ExceptionHandlingMiddleware

Он перехватывает непредвиденные исключения, пишет подробности в лог и возвращает клиенту общий `ProblemDetails` со статусом 500. Если ответ уже начал отправляться, middleware не пытается заменить его новым

### 23. Как настроен CORS

В `Program.cs` зарегистрирована политика `Frontend`, которая разрешает origin `http://localhost:5173`, любые заголовки и любые методы. Затем `UseCors("Frontend")` применяет её после `UseRouting`. Другие origin эта политика не разрешает

### 24. Как проверить CORS и почему Swagger недостаточно

Проверка находится в `cors.http`: первый OPTIONS-запрос отправляет `Origin: http://localhost:5173`, второй — `Origin: http://evil.example`. У разрешённого адреса появляется `Access-Control-Allow-Origin`, у постороннего — нет. Успешный Execute в Swagger сам по себе не доказывает CORS, потому что Swagger и API обычно работают с одного origin

## Переменные и термины в коде

| Имя | Что означает |
|---|---|
| `builder` | Настраивает сервисы приложения, подключения и политики |
| `app` | Готовое приложение с настроенным HTTP-конвейером |
| `dto` | Данные запроса, переданные клиентом |
| `db` | `AppDbContext`, через который EF Core читает и сохраняет данные SQLite |
| `spot` | Найденное или создаваемое машиноместо |
| `booking` | Найденная или создаваемая бронь |
| `ParkingSpotId` | Идентификатор места, на которое оформляют бронь |
| `correlationId` | Идентификатор запроса для ответа и поиска в логах |
| `StartAt` и `EndAt` | Начало и конец интервала бронирования |
| `excludedBookingId` | ID текущей брони, которую исключают из проверки при её обновлении |
| `result` | Результат работы сервиса: бронь либо тип и причина отказа |
| `context` | Данные текущего HTTP-запроса внутри middleware или фильтра |
| `next` | Следующее звено HTTP-конвейера, которому middleware передаёт запрос |
| `cancellationToken` | Сигнал отмены операции, например если клиент отключился |

## Что я проверил перед защитой

- Проект собирается командой `dotnet build ParkingApi/ParkingApi.csproj` без предупреждений и ошибок
- Создание места и корректной брони возвращает `201`
- Неверный госномер, короткая длительность и неверный номер места возвращают `400` с ошибками по полям
- Повторная бронь занятого интервала и бронь места резидента без абонемента возвращают `409`
- Переданный и сгенерированный `X-Correlation-ID` совпадает с ID в ответе и виден в консольном логе
- Preflight для `http://localhost:5173` получает разрешающий CORS-заголовок, а `http://evil.example` — нет

Для показа преподавателю успешные и ошибочные запросы можно выполнить в Swagger, а оба OPTIONS-запроса — только из `cors.http`
